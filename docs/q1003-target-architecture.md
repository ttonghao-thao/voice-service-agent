# q1003 架构改进与实施方案

2026-10-15，代码核对基线 `63e7059`。本文维护改进决策、实施依赖和退出条件；当前实现见 [架构](architecture.md)，现场事实见 [10 月 14 日证据](voicechat-validation-20261014.md)，状态只在 [任务板](TASK_BOARD.md) 更新。以下方案未因写入文档而实现或通过 GPU 验证。

## 1. 目标与架构判断

当前系统定位是**英文全双工知识客服**：支持并行收音与播放，在正常对话阶段保留停顿、插话和让话，以授权 CueKB 证据回答；用户应听到完整、准确且属于当前请求的语音，失败有明确原因并可恢复。工具等待阶段的语音修订受 Provider 能力限制，不能由“全双工”推定已经支持所有阶段的插话。

中文不是当前实现或验收承诺。是否可扩展到中文，首先取决于后端全双工模型及其运行时的中文语音理解、识别、生成、轮次控制和工具调用能力，必须针对实际部署版本验证。模型支持是必要条件；本项目现有 en-US 提示、ASCII 工具载荷/历史过滤和口述约束也需相应适配与回归，不能仅更换界面语言或语言配置就声明支持中文。

保留 VoiceChat、CueKB 独立部署，以及 Gateway → Coordinator → Runtime → Registry。当前故障没有证据要求拆出更多服务、增加分类模型或子 Agent。需要加强的是边界契约和状态管理：

| 架构缺口 | 对目标与故障的影响 | 处理方向 |
| --- | --- | --- |
| 企业知识执行依赖模型主动调用工具 | 模型全 PAD 时业务链没有启动；严格授权能拒答但不能提高调用成功率 | 核验模型接线与原生调用质量；设能力退出门槛 |
| general_qa 用归属校验授权普通回答 | 唯一 input/response 只证明归属，不能证明公司事实有依据 | 当前企业验证采用 knowledge_required；不把 prompt 当事实门禁 |
| 辅助 RNNT final 是应用业务输入 | RNNT 不直接输入 VoiceChat 主干，但其错误会影响应用查询和来源条件 | 按 PCM→encoder→RNNT 首差异定位，关键条件不确定时澄清 |
| 文本、渲染、协议、播放分别结束 | 文本不再增长或 TTS 强制静音后，响应仍可能不结束 | 明确完成原因和音频排空；独立管理阶段预算 |
| 工具后实际口述在音频结束后检查 | 外置拟文本有证据，不保证 VoiceChat 实际说出的内容；失败无法撤回已播部分 | 如实记录限制；有播前准确性要求时评估受控播报 |
| NVIDIA 续答缺显式 parent_call_id | 单个续答许可可消除多许可歧义，但不能证明未知迟到响应必属新任务 | 保守限制并行、复核 epoch/revision；无法安全关联时关闭旧连接 |

## 2. 本阶段选择及推迟的方案

本阶段以已有 `dual_tools + knowledge_required` 建立最小知识闭环。工具目录来自后台，名称 dual_tools 不限制工具数量；direct 知识实现在严格策略下转外置执行。策略在新 Conversation 中快照，旧会话不会随环境变量切换。

这是输出保护，不是强制工具调用，也不是逐字播报保证。当前 Gateway 会拒绝用户输入后未授权的非空普通输出，包括模型自行生成的问候；工具关联的固定 ACK 另按现有规则处理。

旧方案将 `social_only + 输入白名单 + 响应隔离` 设为首阶段生产默认，本次改为**推迟评审**：ASR 可能遗漏业务尾句，且即便输入只是 Hello，开放式模型回答仍可能包含产品事实。输入分类不足以授权任意生成音频。未来若支持社交直答，应先限定服务端批准的话术或验证播前内容控制；“请求重复”还必须复核被重复答案的来源与权限。不能仅匹配关键词后解锁流式音频。

有界响应隔离只可用于明确的关联/验证等待，不会促使 function head 调用工具。没有证据证明工具只是迟到前，不为消除失败而增加一个全局缓冲层；它会增加首包延迟、内存和取消清理复杂度。

## 3. 可实施的契约改进

### 3.1 策略与提示一致

`voice/provider.py::session_update` 和两份 voice prompt 已移除严格模式下自由问候、澄清、限制说明和自由等待语的许可，与 Gateway 拒绝未授权非空输出的规则一致。有匹配工具时调用并保留完整请求，不能漏掉问候后的产品问题；只口述授权工具结果中的答案/澄清/错误，等待中只使用当前工具关联的固定 `ack_messages`。无匹配工具时不口述、不虚构或借用无关工具；未授权错误与澄清留给门户文字入口。legacy 仍要求每个完整输入先经 bridge，即使调用 Provider 时传入 general_qa 也不放宽。

本次没有新增无匹配工具或模型沉默时的自动文字澄清、响应起始超时，也不改变 general_qa 的一般直答许可。该修正不能宣称修复 function 全 PAD，不能保证未知请求都有匹配工具，也不能保证实际口述逐字准确。

测试范围：两种现有策略、legacy、多工具目录、无匹配工具、纯问候、混合产品请求、空输出和固定 ACK。修改提示后重新注册并新建 conversation；将它作为单独实验变量，不与 PAD 开关同轮修改后推断因果。

### 3.2 显式响应终态

目标状态为 `等待授权 → 输出中 → 排空中 → 终态`；用户/业务/音频/播放各自维护状态，不由 speech_started 统一取消。终态至少区分原生结束、预算保护结束、中断/取消、协议失败和超时；这些是设计语义，尚非新增的公共枚举。

backend 是模型 EOS/预算 EOS 的来源；WS 负责按 response 顺序发送剩余 PCM 和结束事件；Adapter 负责归一化；Gateway 负责授权与交付终态；浏览器负责实际队列排空估计。结束幂等，已结束 response 不复用，迟到事件不能借用新任务许可。预算 EOS 不应在质量报告中自动算正常完整答案。

现有 PAD 补丁仅在原强制静音预算已满足且无工具/用户活动时插入 EOS，保护条件已做 CPU 回归。真实验证先检查触发时刻、完整听音及工具/插话；若出现截断则撤回开关并修正设计。后续把完成原因带到交付记录时，需设计兼容的外部事件映射，按实际字段变更同步契约/客户端和必要迁移，不能仅凭日志推断已经贯通。

### 3.3 分阶段预算

区分等待首个有效输出、工具执行、答案生成总时长、末尾排空。保留各阶段硬上限；连续静音包不能无限刷新期限。当前 general 回答从首次输出开始设置 10 秒绝对期限，工具执行另有共享业务 deadline，不能把两条路径的时限等同。

PAD 尾部预算随累计内容 token 数增长，约为 `内容 token 数 × ratio × 80 ms` 的连续 PAD 时长，还需加此前生成/流水线耗时。必须用真实分段时间协调它与应用总期限；增大 API 超时不能替代结束事件，减小 ratio 也不能替代完整听音。新配置名称和数值待测量后确定。

### 3.4 输入与原生工具契约

部署身份包括镜像 digest、运行文件/模板 hash、模型与转换产物、tokenizer、融合配置、工具目录 revision 和最终注册快照。工具回显成功只代表传输注册；实际 head/特殊 token/融合/输出需要另外核验。现有产物检查器只做静态检查，不能证明权重已被 GPU 进程加载。

同一失败录音按 [定位方案](voicechat-fault-recovery-design.md) 找首个差异；有原生调用后再检查参数、最终 ASR 绑定、实际检索和同 call 回填。一个输入只启动一个有效业务任务，任务可包含预算内多次检索；并非强制整个对话永远只有一个工具事件。不由 final ASR 合成不存在的原生调用。

## 4. 实施计划与决策门槛

| 顺序 | 工作与代码落点 | 依赖 | 完成依据 |
| --- | --- | --- | --- |
| P0-A | 部署 docs/voicechat 完整文件，核对容器；应用设置严格策略并新建会话 | 已交付文件与现场权限 | 实际 hash/环境/会话策略，不以本地 Git 代替部署 |
| P0-B | 两类隔离实验：严格知识闭环；同文件同配置下 PAD 开关 A/B | P0-A；同录音与关联采集 | 分别确认工具/授权及 EOS/完整音频；严格拒绝可能提前终止收尾观察 |
| P1-A | 修严格提示与授权规则不一致；Provider/prompt 目标测试 | 已由代码确认，可独立编码；验证中单变量 | 不暗示未授权普通口述可交付；失败可恢复，工具前输出不泄漏 |
| P1-B | 按首差异修 ASR 或 function 运行路径 | P0-B 的 PCM/模型/事件证据 | 正确首词/关键条件；真实 native call→CueKB→回填；无文本补写 |
| P1-C | 依据 A/B 结果保留/撤回/调整收尾保护；再实现完成原因与阶段预算 | P0-B，TTS 完整听音 | 无悬挂、无截断、无旧响应重开；预算结束单独统计 |
| P2 | 在 Gateway.stream 内提取响应状态/许可/期限管理，保持单写入器和 Coordinator 提交边界 | 终态语义已确定，相关回归稳定 | 交错事件覆盖重复、迟到、取消、授权变更；不改供应商能力声明 |
| P3 | 真实知识与口述验收；据此决定继续原生模式或启动架构替代评审 | P1 收敛 | 当前故障样本重复通过，再扩展产品/数字/否定/长答/工具等待/断线语料 |

不把所有工作都推迟到 GPU 结果：提示一致性与模块职责有代码依据；但 ASR 算子修复、function 根因和新的预算值必须等证据。Gateway 多个 map/set 的维护复杂度是重构理由，不是本次漏工具或缺 EOS 的已证实根因。

## 5. 架构替代的进入条件

若模型接线、输入、模板均符合契约，原生工具仍不能达到冻结语料的可靠性要求，继续修改 Gateway 无法产生原生调用。若必须保证口述忠于批准答案，而当前开放式续答达不到要求，也不能把 after_audio 检查冒充播前保证。

届时另行评审启动级固定的 `流式 ASR → Coordinator/BusinessRuntime → 受控 TTS` 路径：保留身份、KB 范围、证据、提交/交付台账；由应用确定业务执行和播报文本。它改变原生选工具边界、增加 ASR/TTS 集成与轮次控制工作，必须单独确认范围；不作为当前会话自动 fallback，不假设 VoiceChat 现有接口已支持任意文本受控播报。ASR 质量仍需解决，独立 TTS 也仍需听音验证。

## 6. 放行条件

按 [真实验收清单](development/validation.md) 分开记录：输入正确、原生工具选择/参数、真实授权证据、口述一致性、结束/播放、恢复与并发。当前故障样本至少重复三次；静音变体用于定位边界，不是生产修复。更广语料的分母、版本和目标需在测试前冻结。

未授权输出、错误 KB 范围、旧结果交付、虚假引用和内容截断是阻断项；仅握手成功、合成工具回填、CPU 夹具、正确字幕或 audio.done 都不足以放行。真实结果反驳假设时更新设计和任务状态，不把测试期望改成已观察到的失败行为。
