# 文档维护规则

先核对确认需求和当前源码，再编辑。需求、实现、未实施方案、操作、待办、验证证据分开；不能因文档整理改变业务、预算、协议或验收标准。

## 1. 唯一信息归属

| 信息 | 维护位置 | 不在此处重复 |
| --- | --- | --- |
| 开发约束、稳定需求、读取路线 | AGENTS.md | 测试流水、长架构、命令全集 |
| 导航 | README.md、docs/README.md | 实现和结果正文 |
| 产品需求和验收目标 | delivery.md | 当前环境指标、实施进度 |
| 当前调用链和实际行为 | architecture.md；决定理由在 decisions | 未实现设计当事实 |
| 未实施方案与步骤 | implementation-plan.md | 已完成阶段流水、执行证据 |
| 容器制作、配置、迁移、启动、回滚 | deployment.md | 业务验收通过记录 |
| 未完成事项与完成条件 | TASK_BOARD.md | 已完成里程碑、完整报告 |
| 验证方法、当前证据、保留的正式基线和限制 | validation.md | 多份执行手册或验收归档 |
| Provider/第三方/门户协议 | integration、interfaces、portal-protocol | 复制生成 schema 或全套部署命令 |
| VoiceChat 完整文件/hash/启动 | voicechat 源码、manifest、docker-run.md | 默认上下文和三类能力的替代产品模式 |

## 2. 编辑与读取

先 `rg` 标题/符号，再读相关段落；默认只选索引的一行。外部引用不是递归加载指令。默认跳过归档、生成 JSON、锁文件、夹具、快照和 Git 历史，实际依赖需要时定点扩读。

三类查询和通用知识受控兜底是确认需求；旧默认值、某个原生工具名称/数量、依赖缺失不能缩小它。Provider 的 ASR/协议差异必须标明适用范围。示例配置须说明是完整发布目标还是未完成接入，不能另造“仅知识库”等产品部署模式。

执行记录按“当前结论 → 适用版本/环境 → 证据 → 限制 → 复跑入口”组织，不按聊天轮次追加。保留用户明确要求的原始 1/7 正式基线和失败，不把旧环境 0/14 ASR 当当前部署事实，不把本地/模拟/API 回执写成容器、GPU 或听音通过。

删除被替代/重复正文，历史由 Git 追溯，不重建归档副本。仍运行的兼容路径不能因删除旧说明就声称已删除代码；关键约束、当前操作和必要失败证据必须保留。

## 3. 完成检查

纯文档只改 Markdown，检查本地链接/锚点、代码路径、围栏、Shell 语法、术语/适用范围和 diff；无需跑应用测试，不刷新旧测试的日期。文档检查结果也只记 validation.md。

实现状态变化才更新任务板；契约变更由代码导出并同步客户端；外部 VoiceChat 源码变化须按根 AGENTS.md 同步完整文件、manifest 与运行文档。文档任务不能隐式修改 Dockerfile、env、依赖、运行参数或代码。
